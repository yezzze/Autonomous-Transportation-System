## 🎯 核心架构变化

### 原始 LangManus
```
用户 → Coordinator → Planner → Supervisor ⇄ [Researcher, Coder, Browser] → Reporter
                                   ↓
                          [本地工具：search, python, browser]
```

### 新架构（分布式）
```
用户 → Planner → Executor → Monitor → Reporter
       ↓          ↓          ↑ ↓
   [L3 Registry] [HTTP POST] └─ 循环
                   ↓
              [远程 L3 Agent]
```

## 🔑 关键变化总结

| 项目 | 变化 |

|-----|------|--------|------|

| Executor | 3个专门节点（research/code/browser） | 1个通用远程调用节点 | 🔄 完全重写 |
| Supervisor/Monitor | LLM 决策路由 | 简单逻辑判断 | 🔧 简化 |

| Coordinator | 存在 | 删除 | ❌ 移除 |

| 工具类型 | 原始 | 新版本 |

| 代码执行 | `python_repl_tool`, `bash_tool` | ❌ 删除（远程调用）|

### 4️⃣ Graph 层面

| 方面 | 原始 | 新版本 |
|-----|------|--------|
| 节点数量 | 7个 | 4个 |
| 流程类型 | Supervisor 动态路由 | 线性流程 + Monitor 循环 |
| 起始节点 | `coordinator` | `planner` |
| 工作节点 | `researcher`, `coder`, `browser` | `executor` |
| 路由节点 | `supervisor` | `monitor` |

## 🎯 关键设计决策

### 为什么删除 Coordinator？
分布式版本假设用户请求清晰明确，不需要多轮对话澄清。如需支持，可在 Planner 前添加。

### 为什么简化 Supervisor 为 Monitor？
原 Supervisor 使用 LLM 动态决策，但在任务已预先规划的情况下，简单的逻辑判断更高效。

### 为什么用 Mock 而不是直接实现真实调用？
Mock 模式允许在没有真实 L3 Agent 的情况下验证架构设计，降低开发门槛。

### 为什么不支持并行执行？
串行执行简化了初始实现。并行执行可以作为后续优化添加。
